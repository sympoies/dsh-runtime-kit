## 2026-10-01 - Validated nils-cli 1.31.8 and its read-only guard fixes

### Result

- The validated nils-cli release moves from 1.31.5 to 1.31.8. The signed
  `v1.31.8` tag (commit `f1703a98`), both release archives, and every consumed
  companion digest are bound in the manifest, workflow, acceptance artifacts,
  docs, and assertions. The 1.29.0 minimum is unchanged.
- DSH's Bash tool now admits the read-only shells the agent runtime kit admits
  (agent-runtime-kit #180, #184, #185, ported in sympoies/nils-cli#2001,
  #2010, and #2016), and direct commits and unsafe default-branch delivery
  still block. The `core/hooks/` alignment entry is now `synced`.
- A real-binary regression in `test/policy-parity.test.ts` drives the released
  `agent-hook` through the DSH `tools/pre-execute` ingress in a checkout on its
  default branch, so CI proves both directions at the validated release.

### Why / context

- Before this release, DSH refused read-only shells that mention Git, such as
  `printf "$(git rev-parse HEAD)"`, `[ -x /usr/bin/git ]`, `[[ ... ]]` tests,
  `if`/`while` blocks, installed `git-<name>` extensions, and
  `semantic-commit commit --help`, which made DSH a noisier primary harness
  than the agent runtime kit.
- 1.31.7 was skipped as the pin: it still refused `[[ ... ]]` in the
  project-memory and secret-scan guards and `semantic-commit commit --help` in
  the body gate, and both semantic-commit guards admitted a commit whose
  `--dry-run` flag a redirection pushed into an option value
  (sympoies/nils-cli#2020).
- The closure review of the port found a pre-existing bypass,
  `nocorrect x=1 git commit`, which nils-cli #2010 closed.

### Evidence

- With 1.31.5, the regression blocked 5 read-only shells and admitted
  `nocorrect x=1 git commit -m y`. With 1.31.7, it blocked the two `[[ ... ]]`
  forms and `semantic-commit commit --help`, and admitted
  `semantic-commit commit ... --body-bullet >/dev/null --dry-run`. With 1.31.8,
  `test/policy-parity.test.ts` passes 8/8.
- Not blocking: sympoies/nils-cli#2021. The delivery guard returns context
  rather than block for a process substitution or `$'...'` word in a
  semantic-commit value slot; the body gate already blocks those forms.

## 2026-10-01 - Routed DSH sessions to peer coordination guidance

### Result

- DSH sessions now receive peer-coordination guidance as a packaged policy,
  `agent-docs/PEER_COORDINATION.md`, through
  `runtime_context({ intent: "peer-coordination" })`. It covers the read-only
  session board check, mailbox checkpoints at material boundaries and at least
  every five minutes without interrupting an in-flight operation, and
  disposition replies (`accepted`, `deferred`, `declined`,
  `needs-user-authority`, `completed`, `failed`) sent with the session's own
  `agent-session` identity.
- The home instructions route peer work to that intent and carry the
  checkpoint and disposition invariant. Their byte cap rises from 4,096 to
  4,608 so the shared home rules stay intact.

### Why / context

- A coordinating session cannot dispatch work to DSH until a DSH session
  checks its mailbox and answers requests the way Codex and Claude sessions do.
- Code reading shows that a managed DSH session's Bash tool keeps its own
  `AGENT_SESSION_ID` and capability file, so the mailbox and board commands
  authenticate as that session. `agent-session serve` has no route that
  delivers mailbox reminders to DSH sessions (sympoies/nils-cli#2011), so the
  guidance relies on the session's own checkpoints until that ships.

### Evidence

- Regressions failed first: the catalog routing, budget, DSH-native text, home
  routing, and `runtime_context` enum tests (7 failures).
- The repository catalog smoke resolves `peer-coordination` for DSH from a
  repository with no catalog of its own, with released nils-cli 1.31.5.

## 2026-10-01 - Packaged the home-scoped delivery and task policies for DSH

### Result

- DSH sessions in any repository now receive DSH-native adaptations of the
  agent-runtime kit's home policies from the packaged `agent-docs/` catalog.
  `project-dev` phase `delivery` returns the work modes and Git delivery, the
  new phase `review` returns review convergence and evidence, and the new
  phaseless `devlog`, `external-facts`, `web-testing`, `memory`, and
  `upstream-contribution` intents return one document each.
- `runtime_context` omits `--phase` for a phaseless intent. The mutation
  prerequisite still prepares only the `project-dev` edit contract.
- `docs/compatibility.md` records a disposition for every agent-runtime-kit
  home policy: adapted, DSH-native replacement, pending, or not applicable.

### Why / context

- A DSH session outside this repository received only the 10-line edit
  contract. This repository's `docs/policies/` copies are contributor
  documents that never reach other repositories' DSH sessions.
- Each intent and phase stays within 18 KiB so a call fits the default 20 KiB
  context budget with room for a repository's own documents. The devlog
  capability therefore gets its own intent instead of joining `delivery`.
- DSH has no built-in browser or memory store. Those documents route to a
  mounted browser-use provider or a connected memory MCP server and say so,
  instead of copying another harness's tool names. The intent is named
  `web-testing` because the home-file contract forbids the other harnesses'
  intent names.

### Evidence

- Catalog routing, budget, DSH-native text, home routing, and the
  `runtime_context` schema tests failed first and pass now.
- The repository catalog smoke resolves every new intent and phase with the
  released `agent-docs` from a Git repository that declares no catalog, and
  the returned documents equal the packaged files.

## 2026-10-01 - Retired the plan-issue skills and adopted named work modes

### Result

- DSH sessions now receive the named work modes (`direct`, `issue`,
  `program`, `program/dispatch`) as a packaged delivery-phase policy,
  `agent-docs/WORK_MODES.md`, through
  `runtime_context({ intent: "project-dev", phase: "delivery" })`. The home
  instructions route to it before any issue, tracker, or delivery record.
- `runtime_context` gained an optional `phase` (`edit` by default, or
  `delivery`). The automatic mutation prerequisite still prepares only the
  edit phase, so the injected context stays the compact edit contract.
- Activation now stages every packaged `agent-docs/` policy document. Their
  name-to-digest map joins the asset-set digest as `policy_documents_sha256`
  only when a package ships one, so earlier targets keep their accepted digest
  and rollback to them still verifies.
- Removed `deliver-plan-tracking-issue`, rewrote `deliver-dispatch-plan` on a
  tracker plus lane child issues through `forge-cli`, and added program mode,
  its tracker template, and the tracker row grammar to `issue-follow-up`. No
  bundled skill references `plan-issue`, `plan-tooling`, or the numbered tier
  codes any more, and the manifest no longer declares those commands.

### Why / context

- The validated nils-cli release no longer ships `plan-issue` or
  `plan-tooling`, so two bundled skills called missing commands. The
  agent-runtime kit had already replaced the tier ladder with named modes and
  retired the plan workflow; this ports that change in DSH-native form.
- A delivery-phase policy cannot join the edit phase: the prerequisite injects
  every required edit document before the first mutation within a 20 KiB
  budget. An explicit phase keeps larger delivery policy on demand, which the
  packaged home policies of the same program will reuse.

### Evidence

- Regressions failed first: packaged skills still named the retired workflow,
  `runtime_context` had no `phase`, and the packaged catalog declared no
  work-modes document.
- New operations tests stage two policy documents, roll back to a package
  without them, and reject a replaced or planted document and an undeclared
  `agent-docs` entry.
- The repository catalog smoke resolves `WORK_MODES.md` for DSH in the
  `delivery` phase with the released `agent-docs`.
