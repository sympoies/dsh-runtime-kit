## 2026-09-06 - The shipped sources are TypeScript compiled to `dist/`

**Result**

- Every shipped module (`index`, `policy`, `bin/**`, `src/**`) is now a `.ts`
  source compiled by `npm run build` into `dist/`, and `package.json`
  `main`, `exports` and the two `bin` entries point at the build output. The
  conversion is mechanical and behaviour-preserving by construction: a
  parser-driven codemod (`tools/codemod/jsdoc-to-ts.mjs`) lifted the JSDoc types into
  annotations, and the existing suite is the regression oracle. Typecheck is
  `strict` with zero diagnostics across 65 sources.
- The tarball ships `src/**` beside `dist/**` and declares `dsh.build`, which
  turns on the pack-time freshness gate PR 0 (#206) landed inert. Build
  provenance is written from the `npm pack --dry-run --json` file list, so the
  digest the engine recomputes from the extracted package matches what the
  build recorded. Declaration emit is off: an inferred return type that names
  the global `AbortSignal` cannot be written to a `.d.ts`, and a TypeScript
  consumer resolves types from the shipped sources instead.
- Two runtime defects that only a built tree exposes were fixed on the way.
  Assets resolved through `new URL(..., import.meta.url)` landed inside
  `dist/` once modules moved there at per-file depths, so every packaged asset
  now goes through `packageAsset()` from `src/package-root.ts`, which walks up
  to the directory owning `package.json`. And `supervise-command.mjs` is plain
  JavaScript the build never emits, so the engine resolves it from the shipped
  sources. The deploy dispatcher's engine-root check follows the same split and
  expects `dist/bin/*`.
- Plain-JavaScript consumers (`scripts/*.mjs`, `test/helpers/*.mjs`, the
  tests) import from `dist/`, so the suite exercises what ships; the literal
  source-inspection assertions read `src/**.ts`, which is the tree they were
  written against.

**Why / context**

- Gate 0 on #202 closed the zero-build route for good: Node refuses to strip
  types under any `node_modules` path, and both production surfaces install
  there. The maintainer accepted the build step knowing that `npm run
  typecheck` already covered the shipped surface under `strict`, so the
  conversion buys syntax ergonomics and refactoring precision rather than new

  eleven names, `prepublishOnly` and `prepack` included). The freshness gate is
  what makes an explicit `npm run build` safe: a stale `dist/` is refused as

- The codemod had nine defect classes worth remembering for any future
  mechanical conversion, all caught by the error-count regression rather than

  the parameter required); an arrow with one unparenthesized parameter has no
  closing paren to anchor on; and a "last import line" heuristic for inserting
  an import can land inside a multi-line import.

## 2026-09-06 - Tiered policy enforcement with receipt-bound debug downgrades

**Result**

- The packaged policy now declares the three-tier model accepted on #197 for
  child #199: the seven integrity rules stay `locked`, the eight governed
  delivery seams are `downgrade-only`, the seven reminders stay `locked`, and
  every rule carries a `# tier:` line that `test/policy-parity.test.mjs`
  checks against the table and, when a companion is present, against
  `agent-hook inventory`. nils-cli owns the table and the projection
  ([sympoies/nils-cli#1609](https://github.com/sympoies/nils-cli/issues/1609),
  released in 1.28.1); no policy logic moved into JavaScript.
- `dsh-runtime-kit setup|update --policy-overrides <file>`
  (`dsh-runtime-kit.policy-overrides.v1`, rule id to `advise`) is the only way
  to downgrade a seam. The map is validated against the packaged bundle's
  `override_class` before any mutation, becomes part of the plan target (so the
  plan digest, the receipt, and `activation.json` change with it), and is
  rendered into the digest-bound `agent-hook` config as an `[overrides]`
  table. `doctor` reports `policy.downgrades` and `policy.tier_table_sha256`
  from the inventory and adds the `policy-downgrades-active` advisory while
  staying `healthy`. No environment variable can downgrade anything.
- The policy transport drops the "opaque to multiple classifiers" fallback
  text, which the tiered engine can no longer produce. The decision's
  `enforcement` and `downgraded_by` audit fields are not surfaced: nothing in
  the kit consumes them yet, and an untested documented surface was worth less
  than adding it with its first consumer.
- nils-cli 1.28.1 is the minimum and validated release; two nils behaviours the
  tiers changed are recorded as reduced surfaces (the narrowed unclassifiable-
  shell denial and the advisory `block-direct-python`).

**Why / context**

- Tier B protects delivery discipline, where a violation is visible and
  repairable, so a debugging session may downgrade it as long as the downgrade
  is recorded and acceptance refuses to run under it. Binding the override map
  into the target rather than into a side file is what makes `rollback`
  restore the previous configuration and what keeps the asset-set digest
  honest: a target without overrides keeps the digest the accepted baseline
  computed.
- Runtime-kit validates the override against the packaged bundle's
  `override_class` only so the refusal lands at preview; nils rejects the same
  override at load time (`locked-rule-override`) and owns the tier contract.
- The engine changed two behaviours consumers could observe: an unclassifiable
  Bash command blocks only Tier A groups and the Tier B groups whose subject it
  names, and `block-direct-python` is a reminder. Both are recorded in
  `compatibility/retired-surfaces.json` as reduced surfaces with the 1.28.1
  floor.

**Evidence**

  plain digest cannot apply the downgraded configuration (`plan-drift`), the
  staged config carries exactly one `[overrides."dsh.block-direct-git-commit"]`

## 2026-09-06 - A build step needs a freshness gate, because nothing else will ever run the build

**Result**

- `package.json#dsh.build` now declares build provenance, and the operations
  engine refuses a packed artifact whose declared sources no longer match the
  recorded digest (`build-output-stale`) or whose declaration is unusable
  (`invalid-build-provenance`). A package that declares no `dsh.build` is
  admitted unchanged, so the gate lands inert.
- This is PR 0 of #202, the blocking prerequisite for the TypeScript
  conversion. The rename does not start until it merges.
- Gate 0 re-baselined: head `b30bc6fd`, tree `832ebb47`, package SHA-256
  `815603f14e993a27d13c6c6883b45e00dd879b38c5c7ba8a2deef550bd907925`, rollback
  target `11ab77e1`.

**Why / context**

- The 2026-09-06 entry above established that no npm lifecycle hook can carry a
  build, `prepublishOnly` and `prepack` included. The consequence is sharper
  than it first looks: nothing in the packaging path will ever run a build
  automatically, so a stale output is not an unlikely slip but the default
  outcome of forgetting one command.
- Nothing else catches it. `npm pack --ignore-scripts` copies whatever is on
  disk; the plan digest binds the packed tarball faithfully, whatever it holds;
  the receipt authenticates that same artifact; and the typecheck reads sources,
  not output. Every signal stays internally consistent while the wrong code
  ships. This is the failure shape `AGENTS.md` already documents for skipping
  the `tsdown` stage of the DSH rebuild, and the conversion would otherwise have
  reproduced it inside this repository.
- The gate verifies the *packed* tree rather than the working directory. That
  choice matters: it covers all fourteen `npm pack` call sites through one
  check, including the three that do not pass `--ignore-scripts`, instead of
  requiring each harness to opt in.
- The digest is content-derived on purpose - sorted names, entry kind, symlink
  target, the executable bit, file content - and excludes mtime, inode and the
  rest of the mode. A checkout, a `git stash`, or a `touch` cannot forge
  freshness, which an mtime comparison would have allowed.
- The declaration is deliberately not bound into the reviewed plan. Adding a
  receipt key would break the baseline-engine readability that the existing
  lifecycle binding explicitly protects, and refusing the artifact needs no such
  binding.

**Evidence**

- Five regression tests in `test/operations.test.mjs`, written to fail first:
  stale sources rejected with the profile untouched, matching output admitted,
  an undeclared package still admitted, a malformed declaration refused, and a
  declaration naming a path outside the package refused.
- Digest properties probed directly: identical after `utimesSync` back-dates a
  source, different after a nested file edit, and stable under source-root
  ordering.
- Full suite 798/798 (636 + 99 operations + 63 contract and packaging), exit 0;
  `tsc -p jsconfig.json` clean. Runs were serialized with
  `--test-concurrency=1` because a concurrent suite in another checkout made
  the default concurrency OOM.
- Gate 0 path-pin sweep: `test/` 265 references (81 relative source imports over
  49 targets, 32 literal `src/...js` assertion strings), `docs/` 36,
  `compatibility/` 29, `scripts/` 26, `package.json` 17, `policy/` 3, and zero
  in `agent-docs/`, `skills/` and `cordis.patch.yml`.

## 2026-09-06 - TypeScript is back on, and the blocker was never the digest

**Result**

- Issue #202 reopened and rewritten: the conversion proceeds **with a build
  step**, replacing the closed erasable/no-build outcome. The maintainer
  accepted the cost/benefit explicitly — `npm run typecheck` already covers the
  shipped surface under `strict`, so the conversion buys ergonomics rather than
  new type safety.
- A blocking **PR 0** was added: a content-based pack-time freshness gate must
  merge before any rename.
- #204 landed the prerequisite: `jsconfig.json` now covers `index.js` and
  `bin/**`, which it had never included.

**Why / context**

- The 2026-09-05 entry and `DEVELOPMENT.md` both attributed the no-build
  constraint to "a package digest that is a digest of the reviewed source".
  That attribution is wrong. `src/operations/index.js:1419` resolves registry
  and local targets alike through `npm pack --ignore-scripts`, and the plan
  digest binds the packed tarball and the extracted package-tree identity. It
  guarantees that apply installs exactly the artifact preview reviewed — a
  property that holds identically for build output. A build step costs nothing
  there.
- The real constraint is that no packaging path can run a build at all.
  `INSTALL_LIFECYCLE_SCRIPTS` in `src/operations/index.js` refuses an installed
  package declaring any of `preinstall`, `install`, `postinstall`, `prepare`,
  `preprepare`, `postprepare`, `prepublish`, `prepublishOnly`, `prepack`,
  `postpack` or `dependencies`, so every npm hook that could build is closed.
  A plain `build` script is permitted — it is not a lifecycle name — but nothing
  invokes it automatically. Independently, 11 of the 14 `npm pack` call sites
  pass `--ignore-scripts`; the three that do not
  (`scripts/pack-dsh-compatibility-peers.mjs`, which packs DSH peers rather than
  this tree, plus `test/parity-package.test.mjs` and
  `test/provider-retirements.test.mjs`) gain nothing, because the hooks they
  would run are exactly the refused ones.
- A stale build output would therefore install while the source tree, the
  typecheck, the digest and the receipt all still look correct — the same
  failure shape `AGENTS.md` already documents for skipping the `tsdown` stage of
  the DSH rebuild. Hence PR 0 before the rename: one enforced invariant instead
  of an implicit precondition at every pack site.
- The zero-build route stays closed and was re-verified rather than assumed.
- Excluding `index.js` and `bin/**` from the typecheck had been hiding real
  interface debt, not just missing annotations. Most notably `ctx.llm.guard`
  does not exist in the pinned `@deepseek-ai/dsh-llm` types at all: it is added
  by this repository's own `native-execution-boundaries-v5` patch. That is why
  `src/` duck-types the context instead of naming `Context`, and it tells the
  conversion that the patched runtime surface must be modelled explicitly.

## 2026-09-05 - The sources stay JavaScript: Node will not strip types under node_modules

**Result**

- Issue #202 (convert the package to erasable TypeScript executed by Node,
  no build step) closed as not planned at Gate 0, before any production edit.
  The `// @ts-check` JavaScript sources, `jsconfig.json`, and `npm run
  typecheck` stay as they are; `DEVELOPMENT.md` now records the constraint so
  the idea is not re-spiked against the wrong launch shape.
- The #197 tracker keeps #199 and #198 in JavaScript. Baseline `036d0af5` /
  package `d1f723be` is unchanged.

**Why / context**

- Node's type stripping throws `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`
  for any `.ts` whose real path contains a `node_modules` segment. Both
  production surfaces of this package resolve to one: `setup` installs the
  packed tarball through `dsh plugin add --offline --save-exact`, which pnpm's
  hoisted linker places as a real directory under
  `profiles/<profile>/node_modules/@sympoies/dsh-runtime-kit/`, and the
  operations CLI is installed with `npm install --global`, so `bin/*.ts`
  would resolve under the global prefix's `node_modules`.
- The spike that motivated #202 passed the packed smoke 9/9 with an `index.ts`
  entry because `test/smoke.mjs` launches DSH as `pnpm dsh`, and DSH's `dsh`
  script is `node --import tsx/esm apps/cli/src/bin.ts`. `tsx` transpiles
  every `.ts` it loads, so Node's own type stripping was never on the path. A
  released `dsh` runs `apps/cli/lib/bin.js` under plain `node`, which is what
  `resolveToolchain` requires as an exact reviewed release.

## 2026-09-02 - Replaced the single-workspace lease model with a repository authority set

**Result**

- WorkspaceLease protocol v2. A session's startup cwd is now a contextual
  anchor rather than a permission boundary, and a live DSH lineage owns an
  authority *set*: zero or more lazily acquired repository bindings, each with
  independent identity, generation, fencing, renewal, failure, and release
  state. A lease denial is local to the exact repository target it names, so a
  dirty anchor no longer denies unrelated tools, other repositories, or
  non-repository paths.
- nils-cli gained `agent-hook workspace-lease resolve`, which classifies one
  exact tool execution into canonical repository targets and owns no durable
  state, plus target-scoped v2 `bind`, `begin`, `complete`, `renew`, and
  `release` schemas. The durable per-worktree authority model, fencing,
  idempotency, tombstoning, expiry, and same-session resume recovery are
  unchanged, so one physical worktree still contends across sessions.
- Honest coverage is explicit, and the test is whether an operation's own
  declared arguments prove the repository it mutates — not whether it is a
  shell. Structured `write`, `edit` and `str_replace_editor` mutations qualify
  through their path argument; `artifact_export` qualifies through
  `destination.path` when `destination.class` is `workspace`; and
  `runtime_kit_governed_commit` qualifies through the anchor alone, because it
  has no target to choose and always commits the canonical live Session cwd.
  Read-only forms, unknown tools, and arbitrary shell programs resolve to
  `not-required` and run as unscoped native host operations rather than being
  blocked on an anchor they never touch. Behavioral policy, protected roots,
  secret controls, and signing are unaffected.

**Why / context**

- Issue #172. Under v1 a dirty primary checkout denied the startup bind, and
  every ordinary tool was then denied before its body ran. A later tool
  `workdir`, a clean linked worktree, another repository, or a non-repository
  path could not select an independent authority scope, so one dirty checkout
  made an otherwise full-host session unusable. The #102 quarantine made that
  diagnosable but deliberately could not resume normal work.
- The protocol generation is selected by the request schema, and a declared
  version that disagrees with it is rejected as a mixed-version request. A v1
  provider cannot register with a v2 runtime and vice versa, so no lease token
  or binding crosses generations and existing v1 sessions keep v1 semantics
  until they restart against a matched pair.
- The v2 `bound` result names the exact repository target it owns. Without
  that, the eager anchor binding and a later lazy acquisition of the same
  repository would mint two generations and the session would contend with
  itself; acquisition also now waits for the release of the generation it
  replaces for the same reason.

**Evidence**

- nils-cli: the `nils-agent-hook` suite is green with 23 v2 cases covering
  resolution, symlink and relative convergence, every classified mutation form,
  governed-commit and artifact-export classification including their fail-closed
  paths, cross-repository independence, dirty-target locality, contention,
  target forgery, mixed versions, renew on the v2 result schema, replay,
  release ordering, a same-session re-bind denial, and concurrent first-use
  resolution; `--local-fast` checks green. Delivered as
  `sympoies/nils-cli#1600`.
- Review found two authorization regressions in the first cut of the
  classifier, both of the same class: `runtime_kit_governed_commit` and
  `artifact_export` have provable targets but fell into the unclassified
  catch-all, so v2 stopped coordinating the very operation the lease exists for
  and let an export dirty a checkout another session owned. The fix changed the
  classification axis from "is this a shell" to "do the declared arguments
  prove the target". Creating the private state directory was also made atomic
  at mode 0700: v2 turned every classified tool call into a first-use creator,
  which multiplied a create-then-chmod race into a hard denial of the tool
  call.
- dsh-runtime-kit: 778 of 778 unit tests pass. An earlier run of this branch
  showed one failure, `runtime values are version-bound`, which reproduced
  identically on unmodified `main`; it was a stale local `node_modules` peer
  version and disappeared after a clean install, so it was never a regression
  in this delivery.
- Packed native smoke against real DSH `0.1.2-alpha.4` and the real v2
  provider proved, in one process: a dirty-anchor session wrote a
  non-repository directory and an unrelated clean repository (fenced) while the
  dirty checkout itself stayed denied with `WORKSPACE_DIRTY` and byte-identical

  release and `compatibility/nils-cli.json` pins its artifact digests: runtime
  health authenticates the installed companions against those pins, so the
  bundle refuses to boot with a locally built agent-hook. Release nils-cli
  first, bump the compatibility pin, then run the full keyless E2E and live
  acceptance.
- `sympoies/nils-cli#1606`: a v2 `begin` authenticates the target it is given

  call's own arguments would resolve to, so the fence lands on the workspace
  the runtime **names**. This is defence in depth rather than an authorization
  bypass — the caller is the trusted same-host runtime, which also supplies
  `anchor_cwd` and can reach any repository through the deliberately unfenced
  shell path — but a runtime bug pairing a target with the wrong execution
  would silently fence the wrong workspace instead of failing closed. The fix

## 2026-09-02 - Removed the randomness behind a 1-in-75,000 CI flake

**Result**

- `signingFixture` derives its Ed25519 key from a fixed seed
  (`sha256` of a versioned label) instead of calling `generateKeyPairSync` per
  invocation, so every manager fixture signature is now deterministic. It takes
  an optional `signer` argument for a test that needs a second, unrelated
  signer; `signed documents cannot select a digest-valid bundle outside the
  verified lineage` is the one pre-existing such call site and now asks for
  `'untrusted'`, as does the new determinism test.
- The keypair was the only source of nondeterminism in the signed fixture
  payloads — no `Date.now`, `randomUUID`, `randomBytes`, or `Math.random`
  appears in the fixture module or the three suites that use it — so the flake
  class is gone rather than narrowed.

**Why / context**

- `assertSecretFree` (`src/manager/contracts.js`) rejects any string matching
  its secret patterns, one of which is
  `/(?:^|[^A-Za-z0-9])sk-[A-Za-z0-9_-]{4,}/u`. Fixture signatures are encoded
  `base64url`, whose alphabet includes `-` and `_`, so a random signature could
  contain an `sk-` run preceded by a non-alphanumeric character purely by
  chance and be rejected as a leaked secret.
- Measured at 67 hits in 5,000,000 random 64-byte `base64url` strings, about 1
  in 75,000 signatures. The suite signs many fixtures per run across six CI
  jobs per push, so a red job every so often was expected rather than strange.
- The failure was worth fixing beyond its rate: it reads exactly like a real
  secret leak, it lands on an unrelated PR, and the natural response — re-run
  the job — is also the response that would mask a genuine regression in
  `assertSecretFree`.
- Chose fixed seeds over exempting the signature field from the scan. Exempting
  it would shrink the invariant; seeding removes the randomness and leaves the
  guard covering the same surface. The new test pins both halves: the fixture
  signature is stable and matches none of the secret patterns, and a genuinely
  secret-shaped value on the same field is still rejected with

## 2026-09-02 - Added session-owned artifacts as a native runtime service

**Result**

- Added `dshRuntimeArtifacts`, a runtime-kit-owned native DSH service for
  generated, non-conversational outputs, plus five distinct tools
  (`artifact_write`, `artifact_present`, `artifact_read`, `artifact_export`,
  `artifact_dispose`). References are opaque and non-bearer; content identity
  is a separately verified SHA-256; metadata never carries a storage location.
- Every capability is authorized from the exact live executing agent, so a
  copied reference from another session or workspace is denied before any byte
  is read. Streaming writes stage under a 0700 store root and publish
  atomically; cancelled, interrupted, over-limit, quota-exhausted, and failed
  writes leave nothing readable.
- Two retention classes (`session`, `retained`) reclaim only the targeted
  owner lifecycle; records are revalidated after restart; export writes only
