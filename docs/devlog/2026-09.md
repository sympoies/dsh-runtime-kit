# Development log - 2026-09

## 2026-09-03 - Repaired the DSH rebuild step the validation runbook prescribed

**Result**

- `AGENTS.md` no longer tells readers to run `pnpm run build:lib:host`. On the
  pinned alpha.4 revision that script aborts: it chains `tsc -b` with an
  unfiltered `tsdown` whose root-package entry
  `lib/types/{index,invariant,startup}.js` does not exist, and `tsdown`
  validates entries during config resolution, so no workspace package is
  bundled at all.
- The runbook now names both rebuild stages explicitly and uses
  `tsdown --env.DSH_BUILD_FACE host -F <package>` for every package the active
  patch touches. `-F` selects workspace configs by name and excludes the
  failing root config; the run exits 0 and produces bundles carrying the patch.
- The rollback paragraph no longer implies `npm run test:smoke` can prove a
  rolled-back harness works. The smoke asserts the checkout is `patched` before
  anything runs, so on a pristine checkout it fails closed by design; the
  runbook now says to boot an unpatched `dsh` directly.
- The companion paragraph now lists every sibling the smoke resolves
  (`review-specialists`, `forge-cli`, `main-agent`, `agent-session`, plus
  `GIT_CLI_BIN` for the native lease smoke) and records that companion
  authentication rejects a binary with group- or other-writable ancestor
  directories, which is why a Homebrew `Cellar` install fails as
  `DSH_RUNTIME_HEALTH_COMPANION_IDENTITY_INVALID` despite a correct digest.
- The scope of `test:operations-smoke` is stated: it is a leg of
  `scripts/run-acceptance.mjs`, not a standalone command.

**Why / context**

- The #172 delivery could not run the packaged smoke, and the cause was
  recorded twice as "DSH cannot be rebuilt without changing its build
  configuration, which repository policy forbids". Both records were wrong.
- The real failure was an artifact generation gap. Each package's `exports` `.`
  resolves to `lib/index.js`, produced only by `tsdown` from the `lib/types/*.js`
  that `tsc -b` emits. Applying the patch changes `src/` alone, so a `tsc -b`
  without a completed `tsdown` leaves the runtime importing a pre-patch bundle
  while the source tree, the patch receipt and `lib/types/` all read as correct.
  Every signal an operator would check looked right.
- That is also why the misdiagnosis was durable: the composite `build:lib:host`
  exit code was read as "DSH is not buildable here" rather than "the second of
  two stages aborted, and the first one succeeded".
- Nothing in DSH changed. `-F` is an existing `tsdown` flag, so this stays
  inside the no-fork, no-vendor invariant.

**Evidence**

- `npm run test:smoke` -> `"ok": true`, 9/9 scenarios `passed`,
  `nilsCompatibilityStatus: "released"`, against DSH `0.1.2-alpha.4` at
  `4e84901e` with nils-cli 1.27.37 companions whose digests match
  `compatibility/nils-cli.json` `release.artifacts`. Three independent runs.
- `npm run test:workspace-lease-native-smoke` -> `sameWorktreeDeniedBeforeBody`,
  `distinctWorktreesOverlapped`, `dirtyBootstrapQuarantined`,
  `cleanManagedHandoffVerified`, `dirtyAnchorKeptFullHostAuthority` and
  `crossRepositoryMutationFenced` all true, with the dirty checkout still
  denied. This is the two-repository leg a single-repository smoke cannot
  distinguish from anchor attribution.
- `npm run test:workspace-lease-smoke` -> `protocolVersion` 2.
- Two full reverse -> rebuild -> re-apply -> rebuild cycles; the patched export
  count in `packages/sandbox/sandbox/lib/index.js` moved 3 -> 0 -> 3 and the
  smoke was green after each re-apply.

**Links**

- Issue #185 carries the corrected root cause and the working command.
- Issue #186 records a related contract gap found while diagnosing this: the
  compatibility contract omits `isNonWideningSandboxEcho` while `applyPolicy`
  enforces it, so an unpatched DSH passes the gate and fails later as an
  untyped `TypeError`.

## 2026-09-02 - Attributed finish-line evidence to the repository each edit targets

**Result**

- An edit generation is now recorded against the repository the operation
  targets rather than the session anchor. `bash` validations already bound to
  their own working directory; editor tools expose an exact path but no
  repository root, so the ledger now reuses the canonical target the
  workspace-lease service already resolved and authenticated for that exact
  execution.
- `ctx.workspaceLease.targets(exec)` projects those authenticated roots for one
  exact live execution and memoizes the resolution, so the ledger and the
  service's own admission observe one provider decision instead of paying for
  two classifications.
- An operation the provider proved touches no repository registers no edit
  generation anywhere, so a non-repository write creates no Git validation
  obligation. An unexpected multi-repository edit target fails closed with
  `finish-line-edit-target-ambiguous` before reserving anything.
- A failed projection propagates the workspace-lease service's own typed cause
  instead of a finish-line reason, so a `WORKSPACE_DIRTY` or
  `WORKSPACE_FOREIGN_ACTIVE` root cause still reaches the model.

**Why / context**

- Issue #178, the one acceptance criterion #172 left open. #172 gave a session
  an authority set, so it can mutate several repositories without restarting;
  the ledger did not follow, and a session anchored in repository A that edited
  repository B recorded that generation under A. Nothing then required B's
  declared validations before the stop boundary.
- This was not a regression: under WorkspaceLease v1 the session could not
  reach repository B at all, so no attribution existed to break.
- The stop boundary and the durable nils state needed no change. Ledgers were
  already keyed by `product + sessionId + cwd` and `turnStopping` already fanned
  across every authoritative ledger in the session, because `bash` `workdir`
  already produced more than one. The gap was only the edit identity, so no
  nils-cli protocol change was required.
- Git identity is deliberately not re-derived in JavaScript. The lease provider
  is the one boundary that canonicalizes an operation target, and reusing its
  decision keeps a single source of truth.

**Evidence**

- A behavioural red first: with the new contract in place and the pre-change
  coordinator, four cases failed, including the edited repository being ignored
  in favour of the anchor.
- `test/finish-line.test.mjs` covers target attribution, the non-repository
  no-obligation rule, the ambiguous-target refusal, per-repository stop and
  release fan-out, and the unchanged anchor behaviour for an embedder that
  composed no lease service.
- `test/finish-line-repository-scope.test.mjs` composes the real
  `WorkspaceLease` service and the real coordinator with the production wiring,
  so the seam under test is the shipped one rather than an injected double.
- `test/workspace-lease.test.mjs` proves one execution resolves its targets
  once for both the ledger and the admission, that an unscoped operation
  projects none, and that the projection is refused for anything but one exact
  live execution.
- Packed regression against real DSH `0.1.2-alpha.4` with the v2 provider: the
  native workspace-lease smoke and the packed bundle smoke both still pass, so
  the memoized resolution did not change admission behaviour.

**Follow-ups**

- The full keyless `npm run test:smoke` leg that would exercise a two-repository
  turn through the real bundle still depends on the nils-cli release that #172
  needs; it runs once the compatibility pin moves.

## 2026-09-02 - Replaced the single-workspace lease model with a repository authority set

**Result**

- WorkspaceLease protocol v2. A session's startup cwd is now a contextual
  anchor rather than a permission boundary, and a live DSH lineage owns an
  authority *set*: zero or more lazily acquired repository bindings, each with
  independent identity, generation, fencing, renewal, failure, and release
  state. A lease denial is local to the exact repository target it names, so a
  dirty anchor no longer denies unrelated tools, other repositories, or
  non-repository paths.
- nils-cli gained `agent-hook workspace-lease resolve`, which classifies one
  exact tool execution into canonical repository targets and owns no durable
  state, plus target-scoped v2 `bind`, `begin`, `complete`, `renew`, and
  `release` schemas. The durable per-worktree authority model, fencing,
  idempotency, tombstoning, expiry, and same-session resume recovery are
  unchanged, so one physical worktree still contends across sessions.
- Honest coverage is explicit, and the test is whether an operation's own
  declared arguments prove the repository it mutates — not whether it is a
  shell. Structured `write`, `edit` and `str_replace_editor` mutations qualify
  through their path argument; `artifact_export` qualifies through
  `destination.path` when `destination.class` is `workspace`; and
  `runtime_kit_governed_commit` qualifies through the anchor alone, because it
  has no target to choose and always commits the canonical live Session cwd.
  Read-only forms, unknown tools, and arbitrary shell programs resolve to
  `not-required` and run as unscoped native host operations rather than being
  blocked on an anchor they never touch. Behavioral policy, protected roots,
  secret controls, and signing are unaffected.

**Why / context**

- Issue #172. Under v1 a dirty primary checkout denied the startup bind, and
  every ordinary tool was then denied before its body ran. A later tool
  `workdir`, a clean linked worktree, another repository, or a non-repository
  path could not select an independent authority scope, so one dirty checkout
  made an otherwise full-host session unusable. The #102 quarantine made that
  diagnosable but deliberately could not resume normal work.
- The protocol generation is selected by the request schema, and a declared
  version that disagrees with it is rejected as a mixed-version request. A v1
  provider cannot register with a v2 runtime and vice versa, so no lease token
  or binding crosses generations and existing v1 sessions keep v1 semantics
  until they restart against a matched pair.
- The v2 `bound` result names the exact repository target it owns. Without
  that, the eager anchor binding and a later lazy acquisition of the same
  repository would mint two generations and the session would contend with
  itself; acquisition also now waits for the release of the generation it
  replaces for the same reason.

**Evidence**

- nils-cli: the `nils-agent-hook` suite is green with 23 v2 cases covering
  resolution, symlink and relative convergence, every classified mutation form,
  governed-commit and artifact-export classification including their fail-closed
  paths, cross-repository independence, dirty-target locality, contention,
  target forgery, mixed versions, renew on the v2 result schema, replay,
  release ordering, a same-session re-bind denial, and concurrent first-use
  resolution; `--local-fast` checks green. Delivered as
  `sympoies/nils-cli#1600`.
- Review found two authorization regressions in the first cut of the
  classifier, both of the same class: `runtime_kit_governed_commit` and
  `artifact_export` have provable targets but fell into the unclassified
  catch-all, so v2 stopped coordinating the very operation the lease exists for
  and let an export dirty a checkout another session owned. The fix changed the
  classification axis from "is this a shell" to "do the declared arguments
  prove the target". Creating the private state directory was also made atomic
  at mode 0700: v2 turned every classified tool call into a first-use creator,
  which multiplied a create-then-chmod race into a hard denial of the tool
  call.
- dsh-runtime-kit: 778 of 778 unit tests pass. An earlier run of this branch
  showed one failure, `runtime values are version-bound`, which reproduced
  identically on unmodified `main`; it was a stale local `node_modules` peer
  version and disappeared after a clean install, so it was never a regression
  in this delivery.
- Packed native smoke against real DSH `0.1.2-alpha.4` and the real v2
  provider proved, in one process: a dirty-anchor session wrote a
  non-repository directory and an unrelated clean repository (fenced) while the
  dirty checkout itself stayed denied with `WORKSPACE_DIRTY` and byte-identical
  on disk; two distinct worktrees mutated concurrently through DSH's real
  `write` tool with overlapping fences; a second session on the same physical
  worktree was denied `WORKSPACE_FOREIGN_ACTIVE` before any body ran; and the
  `skill`, `runtime_context`, goal, recovery, and clean-handoff surfaces kept
  working.

**Follow-ups**

- `npm run test:smoke` cannot run until nils-cli ships the v2 provider in a
  release and `compatibility/nils-cli.json` pins its artifact digests: runtime
  health authenticates the installed companions against those pins, so the
  bundle refuses to boot with a locally built agent-hook. Release nils-cli
  first, bump the compatibility pin, then run the full keyless E2E and live
  acceptance.
- `sympoies/nils-cli#1606`: a v2 `begin` authenticates the target it is given
  against the durable binding but does not prove that target is the one this
  call's own arguments would resolve to, so the fence lands on the workspace
  the runtime **names**. This is defence in depth rather than an authorization
  bypass — the caller is the trusted same-host runtime, which also supplies
  `anchor_cwd` and can reach any repository through the deliberately unfenced
  shell path — but a runtime bug pairing a target with the wrong execution
  would silently fence the wrong workspace instead of failing closed. The fix
  is an authenticated resolve token keyed over the exact call facts, and it
  lands with its runtime side rather than alone.
- `sympoies/nils-cli#1605`: protocol generations are selected from an untyped
  `version: u64` whose every `else` branch is v1, so a future v3 would silently
  inherit v1 result schemas and v1 semantics at any site an author forgets.
  Deferred because v3 does not exist and the present behaviour is pinned by
  both suites.

## 2026-09-02 - Removed the randomness behind a 1-in-75,000 CI flake

**Result**

- `signingFixture` derives its Ed25519 key from a fixed seed
  (`sha256` of a versioned label) instead of calling `generateKeyPairSync` per
  invocation, so every manager fixture signature is now deterministic. It takes
  an optional `signer` argument for a test that needs a second, unrelated
  signer; `signed documents cannot select a digest-valid bundle outside the
  verified lineage` is the one pre-existing such call site and now asks for
  `'untrusted'`, as does the new determinism test.
- The keypair was the only source of nondeterminism in the signed fixture
  payloads — no `Date.now`, `randomUUID`, `randomBytes`, or `Math.random`
  appears in the fixture module or the three suites that use it — so the flake
  class is gone rather than narrowed.

**Why / context**

- `assertSecretFree` (`src/manager/contracts.js`) rejects any string matching
  its secret patterns, one of which is
  `/(?:^|[^A-Za-z0-9])sk-[A-Za-z0-9_-]{4,}/u`. Fixture signatures are encoded
  `base64url`, whose alphabet includes `-` and `_`, so a random signature could
  contain an `sk-` run preceded by a non-alphanumeric character purely by
  chance and be rejected as a leaked secret.
- Measured at 67 hits in 5,000,000 random 64-byte `base64url` strings, about 1
  in 75,000 signatures. The suite signs many fixtures per run across six CI
  jobs per push, so a red job every so often was expected rather than strange.
- The failure was worth fixing beyond its rate: it reads exactly like a real
  secret leak, it lands on an unrelated PR, and the natural response — re-run
  the job — is also the response that would mask a genuine regression in
  `assertSecretFree`.
- Chose fixed seeds over exempting the signature field from the scan. Exempting
  it would shrink the invariant; seeding removes the randomness and leaves the
  guard covering the same surface. The new test pins both halves: the fixture
  signature is stable and matches none of the secret patterns, and a genuinely
  secret-shaped value on the same field is still rejected with
  `secret-shaped-value`.

**Evidence**

- Regression first: the determinism test failed against the random-keypair
  fixture (`expected the second signingFixture() publicKeyHex to equal the
  first`) before the production edit.
- `node --test` over the three suites that use the fixture: 49 pass / 0 fail.
- `npm test` 795 pass / 0 fail, `npm run typecheck` clean,
  `npm run benchmark:policy` within budget.
- Observed originally on PR #174, run `33624311348`, job
  `upstream (upstream-next, 0.1.2-alpha.4, ..., true, 24)`, while the `pinned`
  job passed on the identical revision.

## 2026-09-02 - Gave downstream patches a recorded upstream reference

**Result**

- Both patch manifests accept an optional `upstream_reference` on their patch
  entry (`state`, `url`, `released_in`), validated by a single shared rule in
  `src/compat/upstream-reference.js` that each manifest raises as its own typed
  manifest error. `native-execution-boundaries-v5` and
  `beta-4-runtime-compat-v1` both record `state: "not-reported"`.
- No `schema_version` bump: neither validator ever performed an exact-key check
  on the patch entry, so the field is additive for existing manifests. Absence
  is always valid and never blocks check, apply, reverse, or acceptance.
- `docs/policies/upstream-contribution.md` had already been merged with the
  instruction to record the upstream link "when its manifest supports the
  field". No manifest supported it, so that clause was inert; it now names the
  field and its rules.

**Why / context**

- A patch manifest recorded what a patch changes and which releases it was
  validated against, but nothing about whether the problem was ever reported
  upstream. The removal signal depended on someone remembering. dsh-tui
  `#593` is the precedent: the fix shipped in beta.4 and left the downstream
  diff, but only because that was written into `docs/compatibility.md` by hand.
- `not-reported` is representable on purpose. The escalation policy allows a
  downstream-only concern to stay in a patch and never go upstream, and both
  current patches are in exactly that position; recording the decision keeps it
  distinguishable from an unreported oversight.
- The field is shape-validated but never required, and one object per entry
  rather than a list. Widening to a list is future flexibility with no present
  consumer.
- Considered the devlog instead of the manifest. The argument against the
  manifest — that its other fields are content hashes that never change on
  their own — does not hold, since `validated_releases` and `release_artifacts`
  change on every release promotion. Colocated and machine-readable is what
  makes a removal-signal check possible at all, rather than leaving it to
  memory. Nothing checks it yet: the field is shape-validated and never read
  again, so the removal decision is still manual. An actual gate that flags a
  `merged` reference whose patch is still applied is separate scoped work.

## 2026-09-02 - Added session-owned artifacts as a native runtime service

**Result**

- Added `dshRuntimeArtifacts`, a runtime-kit-owned native DSH service for
  generated, non-conversational outputs, plus five distinct tools
  (`artifact_write`, `artifact_present`, `artifact_read`, `artifact_export`,
  `artifact_dispose`). References are opaque and non-bearer; content identity
  is a separately verified SHA-256; metadata never carries a storage location.
- Every capability is authorized from the exact live executing agent, so a
  copied reference from another session or workspace is denied before any byte
  is read. Streaming writes stage under a 0700 store root and publish
  atomically; cancelled, interrupted, over-limit, quota-exhausted, and failed
  writes leave nothing readable.
- Two retention classes (`session`, `retained`) reclaim only the targeted
  owner lifecycle; records are revalidated after restart; export writes only
  inside the session's canonical workspace, outside protected roots, without
  crossing symbolic links or overwriting, and returns a digest-bound receipt.
- The rollback baseline now pins the exact accepted issue 62 package, and the
  acceptance receipt requires `artifact:*` evidence on the existing `edit`,
  `resume`, and `failure-paths` rows with 14 scenarios and 10 authoritative
  legs unchanged.

**Why / context**

- Released DSH has no generic artifact service: the attachment store accepts
  images only and exposes no delete, streaming, retention, or export
  capability, and the local text-spill locator is a host path. A pre-edit
  probe against pristine rc.7 failed all eight artifact-service assertions.
- Unlike the restricted-role work, no authority has to be composed inside a
  DSH-owned transaction. Cordis service registration, `ctx.tools.register`
  with per-call agent identity, the agent lifecycle events, live-agent
  attestation, the sandbox policy service, and the accepted protected-root
  seam are all public, so the service ships as native bundle code with no new
  DSH source patch; the accepted v5 compatibility distribution is unchanged.
- `session`-class artifacts are reclaimed when the owner agent is disposed and,
  deterministically, by the sweep at the next service start for every service
  generation whose owning process is provably gone. The disposal reclaim alone
  was not enough because it is not guaranteed on every host exit path (the
  Agent Console variant of the packed smoke proved an undisposed record survived
  process exit), and an unconditional startup reclaim was rejected by red-team
  review because two DSH hosts sharing one home would destroy each other's live
  records. Each service therefore claims its generation with the owning pid for
  its lifetime. A resumed session keeps only `retained` artifacts, which is what
  the packed resume scenario proves.
- Specialist review moved batch reclamation to one index scan per batch, added
  a post-open destination identity check that unlinks the created inode on
  every failure branch, widened the export deny set to the host sandbox
  policy's protected roots plus the store root, and aligned the export
  parameter schema with the exact runtime shapes.

**Evidence**

- `test/artifacts.test.mjs` covers round-trip identity for text, JSON, image
  bytes, and a multi-chunk streamed binary; negative writes with no staging
  leak; cross-session, cross-workspace, unregistered, and malformed reference
  denial; restart revalidation with rewritten, hard-linked, symlinked, and
  malformed records; expiry, explicit, and owner-disposal reclamation;
  concurrent writers and read/dispose races; export safety; store-root trust;
  memory and local provider conformance; and the five tools through the real
  DSH tool pipeline.
- The packed keyless smoke runs a real DSH session that writes, presents,
  reads, exports, and disposes an artifact, proves the download capability and
  a traversal export fail typed before any write, denies a second session's
  copied reference, and revalidates a retained reference in a resumed session
  while the session-class record is already gone.
- The complete runtime-kit suite, type checking, and policy benchmark pass;
  the pristine DSH rc.2 and 0.1.2-alpha.4 checkouts each completed patch
  application, host rebuild, packed smoke, reversal, pristine rebuild, and the
  unpatched CLI boot.

## 2026-09-02 - Promoted DSH alpha.4 into a three-release support window

**Result**

- Promoted DeepSeek Harness 0.1.2-alpha.4 at its exact published revision and
  retired 0.1.0-rc.7, leaving exactly three supported releases: 0.1.0-rc.8,
  0.1.1-rc.2, and 0.1.2-alpha.4.
- Made the rolling policy explicit: every DSH promotion adds the newest
  release and retires the oldest in the same change, keeping validation bounded
  while the host interfaces are still evolving.
- Ported the authenticated native execution-boundary patch to alpha.4 and
  adapted runtime-kit to the new session-event snapshot and symbol-keyed
  follow-up interfaces.
- Removed the already-upstreamed dsh-TUI history-lock compatibility hunk. The
  remaining beta.4 patch owns the independent history permission safeguards and
  a read-only bridge from beta.4's legacy session-event view to alpha.4's public
