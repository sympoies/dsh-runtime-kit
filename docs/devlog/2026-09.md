## 2026-09-11 - Doctor enforces the Agent Console TUI repair state

**Result**

- `doctor` now authenticates the installed TUI package's repair state on the
  `dsh-tui` profile and reports it as `agent_console_tui`. Anything other than
  `patched` makes the profile `needs-attention`.
- `src/compat/dsh-tui-patch.ts` gained a read-only, synchronous
  `inspectDshTuiRepair`, sharing the reviewed manifest with the patch manager
  but invoking no Git and mutating nothing.
- `.gitignore` now ignores `.cache/` and a `node_modules` symlink, so a clean
  checkout stays clean for governed PR delivery.

**Why / context**

- The dsh-TUI 0.10.1 promotion established that `dsh plugin add`
  re-materializes a profile's package tree and can discard the applied
  history-permission repair. `update`, `rollback`, and collateral restore all
  delegate to that command through `runDshMutation`, so a routine profile
  update can silently revert 0700/0600 hardening on files holding raw user
  input.
- **Correction to that promotion's analysis.** It recorded the discard as
  introduced by the 0.10 line. That is wrong. A full two-by-two now shows the
  deciding variable is pnpm store state, not the TUI release: `0.10.0-beta.4`
  and `0.10.1` both preserve the repair when the TUI package is already
  materialized in the resolved store, and both discard it when that add has
  just fetched the package. The earlier control varied the store alongside the
  release, so its conclusion was confounded. The promotion's own first instinct
  — that the behavior is release-independent — was correct, and was
  over-corrected into a wrong claim.
- Why the pinned CI smoke stayed green across earlier promotions is **not
  established**. An earlier draft of this entry attributed it to CI and a
  workstation resolving different pnpm store state, citing `test/smoke.ts`.
  That was wrong twice over: the cited comment documents a different failure
  (an `UnexpectedStoreError` abort) and records that both surfaces end up
  pinned to the checkout's store, and the direction is inverted — a colder
  store is the discarding leg, so CI should have been the failing surface. The
  claim is withdrawn rather than replaced. What is established is the
  two-by-two above; the green history is unexplained.
- Store-state dependence is the strongest argument for enforcing rather than
  documenting: an operator cannot predict whether a given mutation discarded
  the repair, and a local run that preserved it proves nothing about the next.
- That promotion documented a re-apply rule but could not detect a violation:
  `doctor` verified DSH, the runtime-kit tree, assets, and receipts, and never
  the TUI package's target digests. Documentation alone left the hazard live
  for any operator who skipped a step, so the check belongs in the gate.
- The inspection is deliberately separate from `manageDshTuiPatch`. A health
  probe must be synchronous to fold into `diagnose`, must not require Git, and
  must report an unreadable or substituted package as a status rather than
  throwing. The manager keeps its fail-closed mutation contract unchanged.
- `.cache/` is written by the declared validation gate in every checkout and was
  not ignored, so running the gate and then `forge-cli pr deliver` failed with
  `dirty_worktree` on an otherwise clean tree. `node_modules/` with a trailing
  slash also missed the symlink a managed worktree uses to share the primary
  checkout's install. Both were previously worked around in machine-local
  `.git/info/exclude`, which helped one machine and no contributor.

**Evidence**

- Regression first: the new `inspectDshTuiRepair` tests failed against the
  missing export, then passed across all five states plus the symlink refusal.
- New operations coverage proves the fail-closed path end to end — an absent
  and then a substituted TUI package both report `ok: false` and drive the
  profile to `needs-attention`; a non-Agent-Console profile reports
  `not-applicable` so unrelated profiles are unaffected.
- The inspection was also exercised against the authentic 0.10.1 package
  through a real profile lifecycle — absent, then `pristine` after install,
  then `patched` after the repair — so the states are proven on real bytes and
  not only on fixtures.
- The store-state correction rests on a two-by-two of TUI release against pnpm
  store state, each leg digesting `lib/types/history.js` before the repair,
  after it, and after a subsequent `dsh plugin add`.
- The committed `.gitignore` alone keeps the tree clean with both a
  `node_modules` symlink and `.cache/` present; the local `info/exclude`
  workaround was reverted to prove it.
- The complete test suite, type checking, the policy benchmark, and the keyless
  Agent Console smoke pass.

  the session-event bridge" below, whose promotion facts stand but whose
  attribution of the repair discard to the 0.10 line is retracted here, as is

## 2026-09-11 - Promoted dsh-TUI 0.10.1 and retired the session-event bridge

> **Partly superseded.** Two claims in this entry were later disproved, and the
> body below is left unedited as the record of what was believed at the time.
> Wherever it says the repair discard is introduced by, specific to, or a
> property of the 0.10 line, that attribution is wrong: the discard is
> release-independent and depends on pnpm store state. Where it says no
> runtime-kit gate detects the revert, that is no longer true either. See the
> 2026-09-11 entry "Doctor enforces the Agent Console TUI repair state" above.

**Result**

- The Agent Console contract now authenticates the exact
  `@deepseek-harness-tui/dsh-tui@0.10.1` source and npm identities: lightweight
  tag `v0.10.1` at `78081ceb`, plus the published tarball SRI and shasum.
- The installed-package repair is narrowed from two authenticated targets to
  one. Only `lib/types/history.js` remains; the downstream
  `lib/types/dsh-adapter/plugin.js` session-event bridge is gone, and the patch
  is renamed to the release-neutral `legacy-history-permissions-v1`.
- Documentation, compatibility automation, and the retained exact-pin record
  select 0.10.1 as the current Agent Console composition target. The DSH pin
  stays at `0.1.2-rc.1`.
- The Agent Console smoke and the operator runbook now apply the TUI repair
  after the profile's final bundle instead of immediately after the TUI
  archive, and `update`/`rollback` carry an explicit re-apply rule. Both cover
  a discard behavior that the 0.10 line introduces, described below.

**Why / context**

- The 0.10 stable line supersedes beta.4, which was promoted as an explicit
  prerelease. Promotion retargeted from 0.10.0 to 0.10.1 mid-change once 0.10.1
  published, because `lib/types/history.js` is byte-identical between the two
  releases: the patch artifact, its digest, and both target hashes are the same,
  so landing 0.10.0 first would have pinned `main` to a known-superseded release
  and cost a second full promotion pass for a digest swap.
- The downstream `ensureSessionEventsCompatibility` shim existed because the
  beta.4 adapter still read `Session.events`, which DSH deleted in alpha.4 in
  favour of `snapshotEvents()`. The 0.10 line ships upstream's own facade at
  `lib/types/dsh-adapter/compat/liveSession.js`, and `presets.runningPresetOf`
  now resolves the log through `snapshotLiveSessionEvents(session)`. Keeping the
  shim would have redefined `events` on a prototype that upstream no longer
  needs, so the execution boundary was removed rather than rebased.
- The patch id no longer encodes a TUI release. The release is already
  authenticated by `validated_releases` plus `package_json_sha256`, so encoding
  it twice only forced an id rename on every bump.
- The legacy history permission migration has no upstream counterpart, so its
  `upstream_reference` state stays `not-reported` and it is the only remaining
  downstream diff.
- The 0.10 terminal-image stack adds two decoder dependencies absent from
  beta.4 — required `sixel` and optional `sharp` — and 0.10.1 adds none of its
  own. Neither they nor sharp's prebuilt platform packages declare an install,
  preinstall, postinstall, or prepare script, so the Agent Console pnpm
  `allowBuilds` denial set needed no change.
- 0.10.1 widens its DSH peer ranges to admit `0.1.3-alpha.2` and the `0.1.5`
  line. The widening is additive and `0.1.2-rc.1` stays inside every range, so
  it does not pull a DSH promotion into this change.
- The Agent Console smoke could not reach its patch-reverse assertion at all.
  It applied the TUI repair immediately after installing the TUI archive and
  then added the runtime-kit bundle to the same profile; `dsh plugin add`
  reconciles a profile by re-materializing its package tree from the pnpm
  store, which restored the pristine TUI bytes and silently discarded the
  repair. The smoke and the operator runbook now apply the repair after the
  final bundle, which is the only order that survives on a real deployment.
- That discard is a property of the 0.10 line, not of the command in general,
  and it is therefore introduced by this promotion rather than pre-existing.
  An earlier draft of this entry claimed the opposite. The claim was corrected
  after a control experiment: under the outgoing `0.10.0-beta.4` pin the
  patched `lib/types/history.js` survives the same `dsh plugin add`
  (`ec712f5279eb72bf` before and after), while under 0.10.1 it reverts to
  pristine. The exact mechanism was not isolated; the 0.10 line's new `sixel`
  and `sharp` decoder closure altering profile reconciliation is the leading
  hypothesis and nothing more.
- Because the discard is real on the pinned line, runtime-kit's own
  `update`, `rollback`, and collateral restore now carry an explicit re-apply
  rule. All three delegate to `dsh plugin --profile dsh-tui add`
  (`src/operations/index.ts` `runDshMutation`), and no runtime-kit gate detects
  the revert: `doctor` verifies DSH, the installed runtime-kit tree, assets,
  and receipts, but never the TUI package's target digests. Without the rule, a
  routine profile update would silently revert 0700/0600 hardening on files
  holding raw user input. Wiring that check into `doctor` is left as an
  explicit owner scope decision rather than folded into this promotion.

**Evidence**

- Both published tarball digests were recomputed locally: SHA-512 matches the
  registry SRI and SHA-1 matches the recorded shasum, for 0.10.0 and 0.10.1.
- `lib/types/history.js` hashes to `8e13a3c8…` in both 0.10.0 and 0.10.1, and a
  full file diff between the two releases is empty.
- The rescoped patch applies to the pristine target with

## 2026-09-06 - A build step needs a freshness gate, because nothing else will ever run the build

**Result**

- `package.json#dsh.build` now declares build provenance, and the operations

**Why / context**

- The 2026-09-06 entry above established that no npm lifecycle hook can carry a
  build, `prepublishOnly` and `prepack` included. The consequence is sharper

  automatically, so a stale output is not an unlikely slip but the default

  choice matters: it covers all fourteen `npm pack` call sites through one

  target, the executable bit, file content - and excludes mtime, inode and the
  rest of the mode. A checkout, a `git stash`, or a `touch` cannot forge
  freshness, which an mtime comparison would have allowed.

  receipt key would break the baseline-engine readability that the existing

## 2026-09-05 - The sources stay JavaScript: Node will not strip types under node_modules

**Result**

- Issue #202 (convert the package to erasable TypeScript executed by Node,
  no build step) closed as not planned at Gate 0, before any production edit.
  The `// @ts-check` JavaScript sources, `jsconfig.json`, and `npm run
  typecheck` stay as they are; `DEVELOPMENT.md` now records the constraint so
  the idea is not re-spiked against the wrong launch shape.
- The #197 tracker keeps #199 and #198 in JavaScript. Baseline `036d0af5` /
  package `d1f723be` is unchanged.

**Why / context**

- Node's type stripping throws `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`
  for any `.ts` whose real path contains a `node_modules` segment. Both
  production surfaces of this package resolve to one: `setup` installs the
  packed tarball through `dsh plugin add --offline --save-exact`, which pnpm's
  hoisted linker places as a real directory under
  `profiles/<profile>/node_modules/@sympoies/dsh-runtime-kit/`, and the
  operations CLI is installed with `npm install --global`, so `bin/*.ts`
  would resolve under the global prefix's `node_modules`.
- The spike that motivated #202 passed the packed smoke 9/9 with an `index.ts`
  entry because `test/smoke.mjs` launches DSH as `pnpm dsh`, and DSH's `dsh`
  script is `node --import tsx/esm apps/cli/src/bin.ts`. `tsx` transpiles
  every `.ts` it loads, so Node's own type stripping was never on the path. A
  released `dsh` runs `apps/cli/lib/bin.js` under plain `node`, which is what
  `resolveToolchain` requires as an exact reviewed release.
- `--dump-config` is not a load proof for the entry: a `throw` injected at the
  top of the installed entry never fired, because the dump composes the bundle
  layer without importing it. Only a boot imports the entry.
- Alternatives were weighed and declined: a build step contradicts the
  zero-build install contract (`exports` to source, `npm pack
  --ignore-scripts`, `lifecycle-scripts-declared`, digest of reviewed source);
  installing outside `node_modules` behind a symlink would load (Node checks
  the real path) but breaks `setup`'s lockfile check for
  `resolution: {integrity, tarball}`; a DSH loader change is upstream work
  that would still leave the global-install CLI surface broken.

**Evidence**

- Scratch DSH profile on the rc.1 host libraries, Node 24.16.0
  (`process.features.typescript === 'strip'`): plain `node apps/cli/lib/bin.js
  --profile probe --patch <driver overlay>` with the installed entry renamed to
  `index.ts` fails with `failed to import loader entry dsh-runtime-kit
  (@sympoies/dsh-runtime-kit): Stripping types is currently unsupported for
  files under node_modules`; the same launch with `index.js` restored imports
  the entry and proceeds to runtime-kit activation; `node --import tsx/esm
  apps/cli/src/bin.ts` boots the `.ts` entry.
- A scratch package whose `bin` is `bin/cli.ts`, installed with `npm install
  --global --prefix <scratch>`, fails with the same code when the installed
  bin runs; `node bin/cli.ts` on the unpacked copy prints normally.

## 2026-09-02 - Replaced the single-workspace lease model with a repository authority set

**Result**

- WorkspaceLease protocol v2. A session's startup cwd is now a contextual
  anchor rather than a permission boundary, and a live DSH lineage owns an
  authority *set*: zero or more lazily acquired repository bindings, each with
  independent identity, generation, fencing, renewal, failure, and release
  state. A lease denial is local to the exact repository target it names, so a
  dirty anchor no longer denies unrelated tools, other repositories, or
  non-repository paths.
- nils-cli gained `agent-hook workspace-lease resolve`, which classifies one
  exact tool execution into canonical repository targets and owns no durable
  state, plus target-scoped v2 `bind`, `begin`, `complete`, `renew`, and
  `release` schemas. The durable per-worktree authority model, fencing,
  idempotency, tombstoning, expiry, and same-session resume recovery are
  unchanged, so one physical worktree still contends across sessions.
- Honest coverage is explicit, and the test is whether an operation's own
  declared arguments prove the repository it mutates — not whether it is a
  shell. Structured `write`, `edit` and `str_replace_editor` mutations qualify
  through their path argument; `artifact_export` qualifies through
  `destination.path` when `destination.class` is `workspace`; and
  `runtime_kit_governed_commit` qualifies through the anchor alone, because it
  has no target to choose and always commits the canonical live Session cwd.
  Read-only forms, unknown tools, and arbitrary shell programs resolve to
  `not-required` and run as unscoped native host operations rather than being
  blocked on an anchor they never touch. Behavioral policy, protected roots,
  secret controls, and signing are unaffected.

**Why / context**

- Issue #172. Under v1 a dirty primary checkout denied the startup bind, and
  every ordinary tool was then denied before its body ran. A later tool
  `workdir`, a clean linked worktree, another repository, or a non-repository
  path could not select an independent authority scope, so one dirty checkout
  made an otherwise full-host session unusable. The #102 quarantine made that
  diagnosable but deliberately could not resume normal work.
- The protocol generation is selected by the request schema, and a declared
  version that disagrees with it is rejected as a mixed-version request. A v1
  provider cannot register with a v2 runtime and vice versa, so no lease token
  or binding crosses generations and existing v1 sessions keep v1 semantics
  until they restart against a matched pair.
- The v2 `bound` result names the exact repository target it owns. Without
  that, the eager anchor binding and a later lazy acquisition of the same
  repository would mint two generations and the session would contend with
  itself; acquisition also now waits for the release of the generation it
  replaces for the same reason.

**Evidence**

- nils-cli: the `nils-agent-hook` suite is green with 23 v2 cases covering
  resolution, symlink and relative convergence, every classified mutation form,
  governed-commit and artifact-export classification including their fail-closed
  paths, cross-repository independence, dirty-target locality, contention,
  target forgery, mixed versions, renew on the v2 result schema, replay,
  release ordering, a same-session re-bind denial, and concurrent first-use
  resolution; `--local-fast` checks green. Delivered as
  `sympoies/nils-cli#1600`.
- Review found two authorization regressions in the first cut of the
  classifier, both of the same class: `runtime_kit_governed_commit` and
  `artifact_export` have provable targets but fell into the unclassified
  catch-all, so v2 stopped coordinating the very operation the lease exists for
  and let an export dirty a checkout another session owned. The fix changed the
  classification axis from "is this a shell" to "do the declared arguments
  prove the target". Creating the private state directory was also made atomic
  at mode 0700: v2 turned every classified tool call into a first-use creator,
  which multiplied a create-then-chmod race into a hard denial of the tool
  call.
- dsh-runtime-kit: 778 of 778 unit tests pass. An earlier run of this branch
  showed one failure, `runtime values are version-bound`, which reproduced
  identically on unmodified `main`; it was a stale local `node_modules` peer
  version and disappeared after a clean install, so it was never a regression
  in this delivery.
- Packed native smoke against real DSH `0.1.2-alpha.4` and the real v2
  provider proved, in one process: a dirty-anchor session wrote a
  non-repository directory and an unrelated clean repository (fenced) while the
  dirty checkout itself stayed denied with `WORKSPACE_DIRTY` and byte-identical
  on disk; two distinct worktrees mutated concurrently through DSH's real
  `write` tool with overlapping fences; a second session on the same physical
  worktree was denied `WORKSPACE_FOREIGN_ACTIVE` before any body ran; and the
  `skill`, `runtime_context`, goal, recovery, and clean-handoff surfaces kept
  working.

**Follow-ups**

- `npm run test:smoke` cannot run until nils-cli ships the v2 provider in a
  release and `compatibility/nils-cli.json` pins its artifact digests: runtime
  health authenticates the installed companions against those pins, so the
  bundle refuses to boot with a locally built agent-hook. Release nils-cli
  first, bump the compatibility pin, then run the full keyless E2E and live
  acceptance.
- `sympoies/nils-cli#1606`: a v2 `begin` authenticates the target it is given
  against the durable binding but does not prove that target is the one this
  call's own arguments would resolve to, so the fence lands on the workspace
  the runtime **names**. This is defence in depth rather than an authorization
  bypass — the caller is the trusted same-host runtime, which also supplies
  `anchor_cwd` and can reach any repository through the deliberately unfenced
  shell path — but a runtime bug pairing a target with the wrong execution
  would silently fence the wrong workspace instead of failing closed. The fix
  is an authenticated resolve token keyed over the exact call facts, and it
  lands with its runtime side rather than alone.
- `sympoies/nils-cli#1605`: protocol generations are selected from an untyped
  `version: u64` whose every `else` branch is v1, so a future v3 would silently
  inherit v1 result schemas and v1 semantics at any site an author forgets.
  Deferred because v3 does not exist and the present behaviour is pinned by
  both suites.

## 2026-09-02 - Removed the randomness behind a 1-in-75,000 CI flake

**Result**

- `signingFixture` derives its Ed25519 key from a fixed seed
  (`sha256` of a versioned label) instead of calling `generateKeyPairSync` per
  invocation, so every manager fixture signature is now deterministic. It takes
  an optional `signer` argument for a test that needs a second, unrelated
  signer; `signed documents cannot select a digest-valid bundle outside the
  verified lineage` is the one pre-existing such call site and now asks for
  `'untrusted'`, as does the new determinism test.
- The keypair was the only source of nondeterminism in the signed fixture
  payloads — no `Date.now`, `randomUUID`, `randomBytes`, or `Math.random`
  appears in the fixture module or the three suites that use it — so the flake
  class is gone rather than narrowed.

**Why / context**

- `assertSecretFree` (`src/manager/contracts.js`) rejects any string matching
  its secret patterns, one of which is
  `/(?:^|[^A-Za-z0-9])sk-[A-Za-z0-9_-]{4,}/u`. Fixture signatures are encoded
  `base64url`, whose alphabet includes `-` and `_`, so a random signature could
  contain an `sk-` run preceded by a non-alphanumeric character purely by
  chance and be rejected as a leaked secret.
- Measured at 67 hits in 5,000,000 random 64-byte `base64url` strings, about 1
  in 75,000 signatures. The suite signs many fixtures per run across six CI
  jobs per push, so a red job every so often was expected rather than strange.
- The failure was worth fixing beyond its rate: it reads exactly like a real
  secret leak, it lands on an unrelated PR, and the natural response — re-run
  the job — is also the response that would mask a genuine regression in
  `assertSecretFree`.
- Chose fixed seeds over exempting the signature field from the scan. Exempting
  it would shrink the invariant; seeding removes the randomness and leaves the
  guard covering the same surface. The new test pins both halves: the fixture
  signature is stable and matches none of the secret patterns, and a genuinely
  secret-shaped value on the same field is still rejected with
  `secret-shaped-value`.

**Evidence**

  fixture (`expected the second signingFixture() publicKeyHex to equal the

## 2026-09-02 - Added session-owned artifacts as a native runtime service

**Result**

- Added `dshRuntimeArtifacts`, a runtime-kit-owned native DSH service for
  generated, non-conversational outputs, plus five distinct tools
  (`artifact_write`, `artifact_present`, `artifact_read`, `artifact_export`,
  `artifact_dispose`). References are opaque and non-bearer; content identity
  is a separately verified SHA-256; metadata never carries a storage location.
- Every capability is authorized from the exact live executing agent, so a
  copied reference from another session or workspace is denied before any byte
  is read. Streaming writes stage under a 0700 store root and publish
  atomically; cancelled, interrupted, over-limit, quota-exhausted, and failed
  writes leave nothing readable.
- Two retention classes (`session`, `retained`) reclaim only the targeted
  owner lifecycle; records are revalidated after restart; export writes only
  inside the session's canonical workspace, outside protected roots, without
  crossing symbolic links or overwriting, and returns a digest-bound receipt.
- The rollback baseline now pins the exact accepted issue 62 package, and the
  acceptance receipt requires `artifact:*` evidence on the existing `edit`,
  `resume`, and `failure-paths` rows with 14 scenarios and 10 authoritative
  legs unchanged.

**Why / context**

- Released DSH has no generic artifact service: the attachment store accepts
  images only and exposes no delete, streaming, retention, or export
  capability, and the local text-spill locator is a host path. A pre-edit
  probe against pristine rc.7 failed all eight artifact-service assertions.
- Unlike the restricted-role work, no authority has to be composed inside a
  DSH-owned transaction. Cordis service registration, `ctx.tools.register`
  with per-call agent identity, the agent lifecycle events, live-agent
  attestation, the sandbox policy service, and the accepted protected-root
  seam are all public, so the service ships as native bundle code with no new
  DSH source patch; the accepted v5 compatibility distribution is unchanged.
- `session`-class artifacts are reclaimed when the owner agent is disposed and,
  deterministically, by the sweep at the next service start for every service
  generation whose owning process is provably gone. The disposal reclaim alone
  was not enough because it is not guaranteed on every host exit path (the
  Agent Console variant of the packed smoke proved an undisposed record survived
  process exit), and an unconditional startup reclaim was rejected by red-team
  review because two DSH hosts sharing one home would destroy each other's live
  records. Each service therefore claims its generation with the owning pid for
  its lifetime. A resumed session keeps only `retained` artifacts, which is what
  the packed resume scenario proves.
